# Multi-agent Collaboration Rules

readme.fm에서 사용자는 PM으로서 문제, 우선순위, 완료 기준을 결정한다. 메인 Codex는 개발 리드로서 작업을 분해하고, 필요한 전문 역할의 검토를 취합해 최종 구현과 검증을 책임진다.

## Roles

| 역할 | 책임 | 기본 작업 방식 |
| --- | --- | --- |
| 메인 Codex | 요구사항 정리, 역할 호출, 설계 결정, 구현·검증·보고 | 구현 담당 |
| 프론트엔드 엔지니어 | 사용자 흐름, 컴포넌트 경계, 상태·오류 UI, 접근성 검토 | 검토 우선 |
| 백엔드·연동 엔지니어 | API 경계, 입력·응답 검증, 비밀 관리, 오류 계약 검토 | 검토 우선 |
| PR 리뷰어 | 완료된 변경의 회귀·품질 검토 | 기존 `pr-review` Skill 사용 |

프로젝트 전용 Codex 하위 에이전트는 `.codex/agents/`에 둔다. 현재 구성은 `frontend_engineer`, `backend_engineer`, `integration_reviewer`이며, 역할별 Skill은 각 에이전트의 세부 작업 기준을 제공한다.

## Operating Model

- 역할은 상시 실행되는 별도 프로세스가 아니라, 메인 Codex가 작업에 맞게 호출하는 전문 하위 에이전트다.
- 단순 UI·문서·Git 작업은 메인 Codex 또는 해당 한 역할만 처리한다.
- 프론트와 서버 경계가 있는 기능은 `frontend_engineer`, `backend_engineer`, 필요 시 읽기 전용 `integration_reviewer`가 먼저 독립적으로 검토하고, 메인 Codex가 결정한다.
- 같은 파일을 여러 역할이 병렬로 수정하지 않는다. 검토는 병렬로 가능하지만 구현은 파일 소유자가 명확한 한 역할만 수행한다.
- 역할 간 의견이 다르면 메인 Codex가 요구사항, 코드 근거, 위험도를 기준으로 선택하고 이유를 보고한다.

## Review Output

검토 역할은 아래 형식으로만 결과를 전달한다.

1. 권장 구조 또는 계약
2. 위험 요소와 필요한 검증
3. 메인 Codex가 결정해야 할 미확정 사항

확정되지 않은 제품 정책, DB 스키마, 외부 API 계약을 역할이 임의로 확정하지 않는다.

## Safety and Ownership

- 모든 역할은 최상위 `AGENTS.md`와 해당 Skill을 따른다.
- API 키, Supabase 서비스 역할 키, 개인 정보는 어떤 역할도 코드·문서·커밋에 넣지 않는다.
- 외부 서비스 생성·수정은 메인 Codex가 전체 초안을 제시하고 사용자 승인을 받은 뒤에만 수행한다.
- YouTube 응답과 사용자 입력은 백엔드·연동 역할이 신뢰하지 않는 데이터로 취급하고 검증 기준을 제안한다.
- PR 생성과 최종 코드 리뷰는 기존 GitHub·PR 리뷰 절차를 사용한다.
